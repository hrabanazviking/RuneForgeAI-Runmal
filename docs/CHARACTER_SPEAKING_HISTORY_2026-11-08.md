## What landed

`src/runmal/faces/character_speaking_history.py` - `resolve_character_speaking_history(session, user_id, character_id)` returns None for a missing, foreign or deleted character (existence never leaks) and otherwise one board document (schema `runmal-p163-character-speaking-history-v1`):

- **The board half**, composed exactly as P-162 composes its silent board - from P-158 directly on this base, since P-162 is not on it: the character's own facts verbatim (`character_to_dict`), one row per owned chat bound to the character in `list_chats` order (creation order; chats bound to other characters and unbound chats never appear), each row carrying the chat's title and message count plus that chat's P-158 history document verbatim in substance - presentation state, current row, every kept event whole with provenance and its entry state judged against today's set and bindings (`still_ready` / `declared_unbound` / `no_longer_declared` / `cleared`), the still-declared entry's descriptor named as data, and P-158's counts plus the kept window per chat. The board is classified under a closed law (`no_chats` / `no_history` / `some_history` / `all_history` - the same strings as P-162's board law, under distinct export names so the two slices stay disjoint), with the totals summed from P-158's own arithmetic and `kept_limit` = P-092's `MAX_HISTORY_KEPT` named once for the board. Events are never merged into one cross-chat stream: interleaving chats would invent an ordering no owner recorded.
- **The voice half**, composed from S512 verbatim in substance, exactly as P-157 / P-159 / P-161 compose it: `resolve_character_voice` for the resolved reference (backend, voice id, language, params) and `get_character_voice` for the stored row, classified under the same closed voice-state law - `profile` (a stored row the resolution used, field-level defaults filling its gaps), `profile_fallback` (a stored row naming a backend outside the known registry - the legacy removed-backend case, where S512 falls the whole reference back to the default), `default_voice` (no stored row at all). The row's named backend rides as `stored_backend` so a fallback is visible, never silent. The P-109 affect view rides whole: affect, source, `consumed: False` and the consumption truth. The voice is stated **once, at board level only**: S512 keys voice by character, so it is identical for every row, and no row and no event carries a voice field of any kind.
- **Voice honesty, as data** - `voice_scope: current_only` rides on EVERY document. S512 stores NO voice history (no versioned rows, no change log, no per-event voice record anywhere in-tree), so the voice half is TODAY'S resolution only: no kept event in any chat is ever claimed to have been spoken in today's voice. The pairing joins a kept past (faces across the character's chats) with a resolved present (voice) and says so.
- **`paired`** - True exactly when a voice resolved (always, for an existing character - a missing profile is the default voice) and the board's kept history holds at least one selection event (total `selection_count > 0`): P-161's pairing law at board level. A cleared-only or empty history never pairs; a voice resolving beside an empty history is stated, never upgraded; neither half is ever substituted for the other.
- **Five standing honesty notes**, fixed order: pairing is data only (no synthesis, no rendering, no lip-sync or animation - no timing contract exists in-tree); the voice is today's resolution only (`current_only`), S512 stores no voice history, the voice is stated once at board level because S512 keys voice by character, and a voice always resolves with the state naming how; every row is P-158's history document composed verbatim, judged against today, never rewritten, with events grouped per chat and never merged; the kept window applies per chat and never claims a complete record; pure read, owner scoped, with the affect carried at `consumed: False`.

## Honest boundaries

- **No voice history is claimed, ever.** This is the slice's binding law, not a limitation paragraph: the document's only temporal half is the face history; the voice is a present-tense resolution, labelled `current_only` in the payload itself so no client can mistake it for a record of how any past moment sounded. The voice appears exactly once, at board level - S512 keys voice by character, and a per-row or per-event voice field would fabricate a record that does not exist.
- **No synthesis, no rendering, no lip-sync.** Synthesis stays with the voice subsystem's live/session machinery; no timing, viseme or animation contract exists anywhere in-tree, so no synchronisation is claimed or faked.
- **No automatic expression detection** - declined ABSOLUTELY under P-092's standing law; nothing scans message text. **No playback or scripting execution** - declined ABSOLUTELY under P-027.
- **No new store, no migration.** Every fact read has exactly one owner already: P-092 for history (via P-158), S512 for voice rows, the chats and characters services for the enumeration and the existence law, P-023 for sprite bytes (never read here).
