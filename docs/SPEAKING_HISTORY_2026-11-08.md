- **The voice half**, composed from S512 verbatim in substance, exactly as P-157 / P-159 compose it: `resolve_character_voice` for the resolved reference (backend, voice id, language, params) and `get_character_voice` for the stored row, classified under the same closed voice-state law - `profile` (a stored row the resolution used, field-level defaults filling its gaps), `profile_fallback` (a stored row naming a backend outside the known registry - the legacy removed-backend case, where S512 falls the whole reference back to the default), `default_voice` (no stored row at all). The row's named backend rides as `stored_backend` so a fallback is visible, never silent. The P-109 affect view rides whole: affect, source, `consumed: False` and the consumption truth. `voice` is None exactly when the chat has no bound character.
- **Voice honesty, as data** - `voice_scope: current_only` rides on EVERY document. S512 stores NO voice history (no versioned rows, no change log, no per-event voice record anywhere in-tree), so the voice half is TODAY'S resolution only: no kept event is ever claimed to have been spoken in today's voice, and no event carries a per-event voice field. - **`paired`** - True exactly when a voice resolved and the kept history holds at least one selection event (`selection_count > 0`). A cleared-only or empty history never pairs; a voice resolving beside an empty history is stated, never upgraded; neither half is ever substituted for the other.
- **Five standing honesty notes**, fixed order: pairing is data only (no synthesis, no rendering, no lip-sync or animation - no timing contract exists in-tree); the voice is today's resolution only (`current_only`), S512 stores no voice history, and a voice always resolves with the state naming how; rows are P-092's kept history verbatim through P-158, judged against today, never rewritten; the kept window never claims a complete record; pure read, with the affect carried at `consumed: False`.

## Honest boundaries

- **No voice history is claimed, ever.** This is the slice's binding law, not a limitation paragraph: the document's only temporal half is the face history; the voice is a present-tense resolution, labelled `current_only` in the payload itself so no client can mistake it for a record of how any past moment sounded.
- **No synthesis, no rendering, no lip-sync.** Synthesis stays with the voice subsystem's live/session machinery; no timing, viseme or animation contract exists anywhere in-tree, so no synchronisation is claimed or faked.
- **No automatic expression detection** - declined ABSOLUTELY under P-092's standing law; nothing scans message text. **No playback or scripting execution** - declined ABSOLUTELY under P-027.
- **No per-expression voices.** S512 keys voice by character only; no per-expression voice record exists, and inventing one would be a new store and a migration - out of scope for this slice.
- **No new store, no migration.** Every fact read has exactly one owner already: P-092 for history, S512 for voice rows, P-023 for sprite bytes (never read here).

## Declined candidates (from the design weighing)

A per-event voice claim or reconstructed voice history (S512 stores none - any such field would fabricate a record; declined ABSOLUTELY under the voice honesty law); a voice-history store + migration (a write-side capture law is a campaign decision, named open); per-expression voices (S512 keys by character only); a client stage/renderer surface (no renderer exists in-tree; a stage re-wraps P-155/P-156); generated expression sprites via P-087 (it lands kind `background` hardcoded through a live plugin instance the faces/app context does not hold - named open); scenario VN stage integration (no record joins scenario cast role names to characters or faces - named open); portrait animation / lip-sync (no timing contract in-tree - unbuildable honestly today); actual TTS synthesis on this road (a history read must not forge a performance).
