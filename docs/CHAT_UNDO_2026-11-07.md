# Chat Undo (P-076) — the coder's journal pattern at chat scale

Undo for chat operations: before a covered operation changes
a chat, the chat's complete prior state is written to a
sealed journal; undo rewinds the chat by exactly one
operation, restoring that prior state in place.

## The pattern

A coder's journal is write-ahead: the before-image is
durable BEFORE the change lands, so the change can always
be taken back. At chat scale the unit of state is the whole
chat, because chat operations interact — a delete renumbers
positions, an edit of a pinned message refreshes its pin
memory. Instead of a hand-proved inverse per operation, one
shared restore path replays a sealed whole-chat snapshot,
so every covered operation is undone exactly, by
construction.

Undo is the rewind verb checkpoints (P-067) deliberately
are not: a checkpoint restores as a NEW chat and discards
nothing; an undo rewinds THIS chat and discards exactly
what the undone operation added. The chat keeps its
identity throughout — same id, same owner; its history,
settings, and pins return to the before-image.

## Storage: sealed files, no migration

One JSON file per journal entry under
`data_dir()/undo/<user_id>/<chat_id>/<entry_id>.json`
(the P-067/P-074 file idiom). An entry carries its
operation name, a per-chat sequence number, ids/indexes
-only detail (never content), and the snapshot payload:
the chat row, every message row in display order, the
chat's tag and organisation rows (P-073), and the pin
memories of the chat's messages (Memory + MemorySource +
MemoryChunk rows), all in the archive's `row_to_dict`
shape. The payload is sealed with a SHA-256 checksum over
its canonical bytes; files are written atomically and are
owner-readable only (0600). Migration head stays 0039.

The stack is bounded at 50 entries per chat; beyond that
the oldest entries are pruned (deleted). A pruned entry is
gone — undo depth is deep, not infinite, and the current
depth is always visible in the journal listing.

## Covered operations

Journaled after validation and no-op checks, before any
mutation — if the journal write fails, the operation
changes nothing:

- Messages: append (including continue/impersonate and
  bridge appends, which land through it), edit, delete,
  move, swipe add / select / delete / import, pin, unpin.
- Chat: rename, author's note, post-history instructions,
  swipe settings, preset, persona, backend profile,
  metadata update, metadata regenerate, favourite.
- Branch rename (the title change on that chat).

No-ops journal nothing: editing to identical content,
moving to the current index, selecting the already-active
swipe, setting the already-active persona, pinning an
already-pinned message, unpinning an unpinned one. Failed
operations (strict-validation refusals) journal nothing.

## Not covered — plainly

- Chat creation and deletion. Deletion is terminal: the
  journal dies with the chat, as its checkpoints and data
  bank do. Undo cannot resurrect a chat.
- Fork, merge-back, copy-to-branch: they create OTHER
  chats. Undo never deletes another chat; the new chat
  carries its own journal from birth.
- Checkpoints and the data bank: separate file systems
  with their own delete verbs.
- Generation itself: a generated turn lands via append,
  and the append is undoable; the backend call, its cost,
  and its session are not.
- Redo. Undo consumes its entry. There is no redo stack.
- Group-room transcripts (a different store).

## Undo semantics

Per-chat, strict LIFO. `POST /chats/{id}/undo` pops the
newest entry, verifies it (envelope, identity binding,
checksum), restores it in one commit, records an
`undo.performed` event, and deletes the entry file. An
explicit `entry_id` must name the top entry — out-of-order
undo is refused (422), because later operations may depend
on the ones above it. Undo is never itself journaled: the
next undo steps one operation further back, never forward.

A corrupt top entry blocks the stack loudly: undo refuses
(422), restores nothing, and consumes nothing. Clearing
the journal (`DELETE /chats/{id}/undo`) is the escape
hatch. Unknown (404) and corrupt (422) stay distinct
everywhere, as house law requires.

Restoring a pinned message's delete brings the pin memory
back with its original id and its search index row
rebuilt; undoing an edit of a pinned message restores the
pin's earlier content the same way.

## API

| Route | Returns |
|---|---|
| `GET /chats/{chat_id}/undo` | `{entries, count, can_undo}`, top first, metadata only |
| `GET /chats/{chat_id}/undo/{entry_id}` | one entry's metadata (verified read) |
| `POST /chats/{chat_id}/undo` | `{undone, entry_id, seq, chat_id, restored_message_count}` |
| `DELETE /chats/{chat_id}/undo` | `{cleared: n}` |

Entry metadata is `{id, chat_id, seq, operation, detail,
created_at, message_count}` — never message bodies, never
the checksum.
