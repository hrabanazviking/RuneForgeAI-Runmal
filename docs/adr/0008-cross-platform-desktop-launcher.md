# ADR-0008 — Cross-platform desktop launcher and browser bootstrap

**Status:** accepted for Distribution campaign D001-D010 (2026-11-01)

## Context

Rúnmál already has a local FastAPI service and browser UI, but the current startup path exposes implementation details to the user: Python installation, a virtual environment, `runmal serve`, a localhost URL, and manual transfer of the local bearer credential into browser local storage.

That is acceptable for development but not for a general-purpose desktop application.

The existing security boundary must remain intact: the permanent local credential may not appear in responses, logs, traces, URLs, exports, or diagnostics, and the service remains loopback-first.

## Decision

1. Add a separate `runmal-launcher` application layer. It manages local server lifecycle and desktop integration without replacing the existing `runmal` CLI.
2. The default desktop shortcut invokes the launcher, not `runmal serve` directly.
3. The launcher starts the server only when it is not already healthy, waits for `/healthz`, and then opens the existing browser UI.
4. Browser onboarding uses a **disposable bootstrap nonce**, not the permanent bearer credential.
5. The launcher writes only a hash of the short-lived nonce plus its expiry to an owner-only file in the Rúnmál data directory. The raw nonce is placed in the loopback bootstrap URL.
6. The server consumes that nonce exactly once and immediately removes its bootstrap record.
7. Successful bootstrap creates a signed browser-session token and sends it as an HttpOnly, SameSite=Strict cookie. The signing key is the existing permanent local credential, which never leaves the server process/data directory.
8. API authentication accepts either the existing bearer credential or a valid browser-session cookie. Bearer auth remains the scripting/bridge-compatible mechanism.
9. When authentication uses the browser cookie, state-changing requests must have a same-origin `Origin` header. Bearer-authenticated clients are not forced into browser-origin semantics.
10. Desktop packaging is platform-native at the outer layer but shares one launcher core across Windows, macOS, and Linux.
11. The launcher records the PID of a server it starts and will only stop a launcher-managed process. It does not scan for and kill arbitrary Python processes.
12. Autostart is opt-in and uses current-user facilities only.

## Why not put the bearer token in the bootstrap URL?

URLs leak into browser history, copied links, diagnostics, referrers, screenshots, and sometimes logs. A permanent secret therefore cannot be used as a convenience parameter.

The one-use nonce is deliberately disposable. Exposure after successful consumption is harmless because the server will reject it.

## Why an HttpOnly session cookie?

The browser needs a credential it can present automatically without JavaScript copying the permanent bearer credential into local storage. A signed HttpOnly cookie:

- is not readable by normal page JavaScript;
- can expire independently;
- can be regenerated by the launcher at any launch;
- does not require storing another permanent server-side secret;
- keeps the existing bearer credential private.

## Consequences

- Existing users/scripts using the bearer credential continue to work.
- The UI can continue sending a bearer header during transition; a valid browser session may satisfy auth when the bearer value is absent or stale.
- Browser state-changing API calls gain a deliberate Origin check when cookie auth is used.
- The launcher bootstrap route is intentionally local-convenience infrastructure and must never be interpreted as permission to expose Rúnmál publicly.
- Packaged applications can hide Python/uvicorn and start the same server internally.
- Code signing/notarization is release infrastructure, not an excuse to weaken runtime behavior when signing credentials are unavailable.
